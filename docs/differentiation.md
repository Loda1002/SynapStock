> "AI가 알아서 매매한다"로 나가면 흔한 트레이딩 봇으로 분류돼 탈락한다(직전 x402 해커톤
> 수상작 16건 중 트레이딩 봇 0건). 다중 에이전트 라운드(차별화 각도 6종 × 심사위원 3인 패널
> + 적대적 탈락 스캔 + 완결성 비평, 에이전트 29개)로 도출한 재포지셔닝 명세.

## 0. 이 전략이 성립하는 근거 — 우리 코드의 실제 결함

숨기지 않는다. **이 목록이 곧 제품 정의다.** 우리가 만들 것은 이 목록을 닫는 레이어이고,
목록의 존재 자체가 "에이전트 결제에 이 레이어가 없다"는 시장 문제의 증거다.

| # | 사실 | 확인한 위치 |
|---|---|---|
| A | **구매자가 브로커의 청구서를 한 글자도 검증하지 않는다** — `reqs.amount`·`pay_to`·`asset`을 그대로 서명 | `agents/trading_agent.py:330-346` |
| B | **AP2 `authorize()`는 `pay_to`를 인자로 받고도 검사하지 않는다.** 검사하는 것은 종목·건별한도·잔여예산 3개뿐 | `payments/ap2_mandate.py:112-129` |
| C | **`allowed_asset`은 코드 전체에서 한 번도 읽히지 않는 죽은 보안 필드** | 정의 `ap2_mandate.py:33`, 직렬화 `:44` — 검증부 없음 |
| D | **`exact` 스킴인데 금액 비교가 `<`** → 초과지불이 통과된다 | `payments/x402_solana.py:180` |
| E | **온체인 tx에 주문 식별자가 없다**(Memo 없음) → 대사(reconciliation) 키 부재, 리플레이 방어 없음 | grep 0건 |
| F | **HTTP 402가 저장소에 한 줄도 없다.** 브로커는 같은 프로세스의 파이썬 객체 | `web/engine.py:750 self._broker.settle(...)` |
| G | **에이전트가 자기 허가서를 자기 키로 서명한다** — `user_pubkey`·서명자·`agent_kp`가 전부 `trading_kp` | `web/engine.py:308,313,314` / `run_demo.py:113` |
| H | 결제 실패해도 AP2 사용액이 환원되지 않는다 | `ap2_mandate.py:128` (되돌리는 코드 없음) |
| I | 배송 실패해도 `status="settled"` | `agents/broker_agent.py:203-216` |

### 결정적 공격 시나리오 (A+B+C 결합)

> 악성 브로커가 **한도 안쪽 금액**(건별 한도 45에 44.94)으로 청구하면서 **수취인을 자기 다른
> 지갑**으로 바꾼다. → AP2는 "44.94 ≤ 45"만 보고 통과시키고, 에이전트는 그대로 서명한다.
> **돈이 나간다. 주식은 오지 않는다.** 한도는 지켜졌는데 전액을 잃는다.

이게 우리 데모의 심장이다. 그리고 이건 우리만의 버그가 아니라 **x402 `exact` 스킴 자체에
counterparty verification 항목이 없다**는 스펙 갭이다 — 스펙은 *파는 쪽*을 보호한다.

## 1. 최종 포지셔닝

### 한 문장

> **x402 결제 스펙은 파는 쪽(resource server)을 보호합니다. 402 Guard는 사는 쪽 —
> 사람 없이 결제하는 AI 에이전트 — 를 보호하는, 돈이 나가기 직전의 마지막 검증 게이트입니다.**

이 문장이 강한 이유: 자기 버그 고백이 아니라 **스펙 갭 지적**이다. 그리고 검증 가능하다.

### 표기 규칙

제출물에서 제품명은 **`402 Guard`** (부제: *에이전트 지출 승인 게이트 — 레퍼런스 시나리오:
토큰화 주식 자동매매*). 저장소명·기존 아카이브는 그대로 둔다.
**"AutoTrader"를 제목 첫 단어로 두면 제목만으로 트레이딩 봇 서랍에 들어간다.**

### README 첫 3줄 (심사위원이 직접 확인하는 경로)

```
# 402 Guard — 에이전트 지출 승인 게이트

x402 exact 스킴은 판매자를 보호하지 구매자를 보호하지 않습니다.
스펙에 counterparty verification이 없어서, 악성 판매자가 한도 안쪽 금액으로
청구서를 위조하면 AI 에이전트는 그대로 서명합니다. 비어 있던 나머지 절반을 구현했습니다.

  curl -i http://<url>/broker/orders      # → 402 Payment Required (원본 응답)
  python scripts/red_team.py --report     # → 공격/차단 매트릭스 + 온체인 재조회
  https://explorer.solana.com/tx/<sig>?cluster=devnet
```

### 첫 화면 KPI 교체 (0시간, 효과 최대)

수익률 차트가 아니라 **`시도 N · 차단 N · 유출 0.00 USDC · 오탐 0`**.
심사위원의 머릿속 폴더가 10초 안에 '봇'에서 '지출 통제'로 옮겨간다.

## 7. 킥오프 심사 프레임 정합 (2026-07-21 발표 3세션 근거)

> 세 발표(Four Pillars 유준혁 / Google Cloud 황선화 / Solana 김채린)가 각기 다른 각도에서
> 한 곳을 가리켰고, 402 Guard 는 그 지점에 정확히 선다. 이 절은 재포지셔닝의 **외부 근거**다
> — 우리 주장이 아니라 주최·재단·구글의 발표에서 나온 프레임에 맞춘다.

### 7-1. "검증·가드레일" 레이어 — 발표자가 콕 집어 추천한 자리

유준혁 세션은 에이전틱 커머스 지형을 5개 레이어로 나눴다: 에이전트 상호운용(A2A) →
커머스·체크아웃(ACP/UCP) → 신원·의도 증명(AP2) → 결제·정산 레일(x402/MPP) →
**검증·가드레일(ARC)**. 그리고 해커톤이 겨냥하기 좋은 셋으로 **커머스·체크아웃 / 신원·의도
증명 / 검증·가드레일**을 명시적으로 추천했다. **402 Guard 는 이 중 '검증·가드레일' 레이어의
구현**이다 — 결제·정산 레일(x402) 위에서 사는 쪽을 검증하는 마지막 게이트. "AI 트레이딩 봇"은
5개 레이어 어디에도 없지만, 402 Guard 는 발표자가 직접 지목한 레이어에 앉는다.

### 7-2. 당위성 — 진짜 해자는 "인증 없는 자율 결제"이고, 그건 검증 계층 없이는 성립하지 않는다

유준혁·김채린 모두 **마이크로페이먼트 논거는 약하다**고 못박았다(카드도 배치정산으로 소액
처리 가능). 진짜 해자는 **인증·로그인 없는 결제 + 저수수료 + 속도**이고 경쟁군은 카드
네트워크다. 그런데 "인증 없는 결제"는 곧 **"사람이 매 건 승인하지 않는 결제"**이고, 승인하는
사람이 없으면 **한 번의 잘못된 서명 = 즉시 온체인 자금 손실**이다(반복·고빈도 자율 결제에서
손실이 누적된다). → 인증 없는 자율 결제를 실제로 **가능케 하려면 사람 대신 청구서를 검증하는
계층이 반드시 있어야 한다.** 402 Guard 가 그 계층이다. 우리는 그 해자를 **부정하는 게 아니라
성립시키는** 쪽에 선다.

### 7-3. "사람 없는 자율성"의 미해결 공백을 정확히 짚는다

세 발표 공통 요구가 **"정책·예산 한도 안에서 사람 승인 없이 에이전트가 직접 서명"**이었다.
Google Cloud 데모조차 자기 결제를 두고 **"사람이 승인하면 버튼 클릭과 다를 게 없다"**고
자평하며, 진짜 자율 결제 예시("재고 0 → 입고 시 자동 결제")를 숙제로 남겼다. 사람을 루프에서
빼는 순간 생기는 공백 = **누가 청구서를 검증하나.** 402 Guard 가 그 공백을 채운다
(check_demand 4항목 + check_delivery 온체인 재조회). "사람 승인 = 버튼 클릭"의 한계를,
우리는 **사람이 미리 서명한 정책을 코드가 매 건 강제**하는 방식으로 넘어선다.

### 7-4. 김채린 "해커톤에서 보고 싶은 것 4가지" 전건 충족

| 관전 포인트 | 402 Guard 의 답 | 증거 |
|---|---|---|
| ① 실제 동작하는 온체인 결제 | localnet 풀사이클(매수 6·매도 1) 온체인 확정 | 교차검증 USDC/주식 PASS, `artifacts/tx/` |
| ② 사람 승인 없는 자율 결제 | 사용자 서명 mandate 한도 내 **에이전트 자율 서명**(사용자≠에이전트 키) | G0 키 분리, `payments/ap2_mandate.py` |
| ③ Solana 결제 스택 | 자체 x402 + AP2 + A2A + USDC(+Memo 대사·exact 정합) | G1~G4 |
| ④ 직관적 UX·명확한 이유 | 첫 화면 KPI = **시도·차단·유출 0.00·오탐 0**(수익률 아님) | `scripts/red_team.py --report` |

김채린은 **"한국은 이미 결제가 편리 → 기존 금융이 혁신 못한 걸 왜 AI로 혁신하나, 그 당위성이
중요"**라 못박았다. 우리 답: **사람이 못 지키는 것(24/7 고빈도 자율 결제의 매 건 청구서 검증)을
코드가 지킨다.** 사람이 개입하는 결제엔 402 Guard 가 필요 없다 — 사람이 빠질 때만 필요하고,
그게 바로 이 대회가 요구하는 미래다.

### 7-5. 프롬프트 인젝션·오남용 방어의 우리 버전

Q&A 에서 pay.sh 는 **"개인키를 에이전트에 안 주고, 유료 엔드포인트 도달 시 사람 생체인증"**으로
방어한다고 했다. 우리는 사람을 다시 부르지 않고 방어한다: **키 분리(G0, 사용자≠에이전트) +
한도(AP2, 사용자 서명) + 청구서 게이트(402 Guard)**. 생체인증이 "매 건 사람을 부르는" 방식이라면,
우리는 **"사람이 미리 서명한 정책을 코드가 매 건 강제"**하는 방식 — 더 자율적이면서 안전하다.
(이 대비는 "왜 우리 방식이 자율성 축에서 더 우월한가"의 근거로 데모/소개서에 쓴다.)
