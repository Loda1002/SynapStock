## 1. 리포트의 전제 4건이 뒤집혔다

### 1-1. ★ "x402 에 이미 구매자 보호가 있다"(리포트 최대 발견 ①) — **반증**

리포트는 `maxAmountRequired` 를 "구매자가 거는 상한"으로 읽고 *"우리 카피가 한 줄로 반박된다"* 고 결론냈다. 스펙 원문 대조 결과:

- `maxAmountRequired` 는 **판매자(resource server)가 402 응답에 실어 내려보내는 요구액**이다. 필드 설명은 `"Required payment amount in atomic token units"` — 한도가 아니라 청구액.
- 결정적으로 facilitator 검증 단계가 **`"Ensure the payment amount meets or exceeds the required amount"`** — `>=` 로 검증되는 **하한(floor)** 이다. 구매자 상한의 **정반대**다.
- 리포트가 인용한 `"The client authorizes a maximum amount"` 는 **`upto` 스킴 한정 문장**이다(FAQ 질문 8 "How should I price my endpoint?"의 스킴별 설명). **우리와 리포트가 다루는 것은 `exact` 스킴**이고, FAQ 는 exact 를 `"a push payment—irreversible once executed"` 로 규정한다.
- 추가 발견: **리포트가 건 출처 URL 이 틀렸다.** v2 스펙 원문에 `maxAmountRequired` 문자열이 **0회** 등장한다(v2 에서 `amount` 로 개명, v1 에는 8회). 우리 `payments/x402_http.py:56` 은 v1 이름을 쓰고 `x402Version: 1` 을 명시 방출한다 — **버전을 선언한 v1 구현이라 밝히면 정합, 숨기면 결함.**

반면 **살아남은 축**(적대 검증에서도 유지): x402 v1·v2·exact 스킴·확장 7종 어디에도 **구매자가 payTo 를 합의 상대와 대조할 의무도, 청구액을 독립 견적과 대조할 의무도 없다.** 유일한 반례 후보였던 `extension-offer-and-receipt` 의 클라이언트 MUST 3개도 전부 *서버 산출물끼리의 내부 대조*이고, 같은 문서가 명시한다 — `"no requirement that clients compare offers against independently obtained prices ... an allowlist of approved payees"`. 그리고 확장 문서의 자백: `"This specification does not mandate a specific authorization mechanism."`

> **판정**: 카피 정정은 필요하지만 **리포트가 말한 이유 때문이 아니다.** 현행 문장("x402 는 파는 쪽을 보호한다")은 *틀려서*가 아니라 *부정확해서* 공격당한다. FAQ 의 구매자 보호 서술 3건(로컬 서명·판매자가 키를 안 가짐·facilitator 변조 시 서명 실패)은 전부 **키 보관(custody)·전송 무결성** 층이고, 우리가 겨냥하는 **거래 상대·청구 내용 검증** 층이 아니다.

### 1-2. AP2 — 리포트가 절반 맞았고, 이유는 달랐다

| 리포트 주장 | 판정 | 근거 |
|---|---|---|
| AP2 스펙에 `allowed payees` 가 이미 있다 | **맞음** | `"The `payee` property of the Payment Mandate MUST be present in the `allowed` array."` 제약 8종(리포트는 6종만 들어 `allowed_pisps`·`reference` 누락) |
| AP2 는 **집행 지점을 규정하지 않는다** | **틀림** | Usage 절이 주체를 못박음 — `"verified by the Credential Provider, Network, and Merchant Payment Processor."` 시점도 MUST(payment credential 반환 **전**). `specification.md` 에 Verification 독립 절, `agent_authorization.md` 에 3단계 검증 절차 + `"Any unknown Constraints MUST be treated as failing evaluation."` |
| "AP2 준수"를 "AP2 개념 기반"으로 낮춰야 한다 | **맞음** | vct 가 `mandate.payment.open.1`/`mandate.payment.1` 로 규정되고 `"Implementations MUST match the exact `vct` string"`. 우리 타입 문자열은 `"open-payment-mandate"`(자체 값), SD-JWT/VC 구조 자체가 없음 |

**리포트가 놓친 반전**: 집행 지점이 규정돼 있다는 사실은 우리에게 **유리**하다. 정확한 명제는 *"AP2 가 공백이다"* 가 아니라 —

> **AP2 는 수취인 제약을 정의하고 그 집행을 Credential Provider·Network·MPP 에 배정한다. 그런데 self-custody 온체인 플로우에는 그 세 주체가 존재하지 않아 집행 지점이 공석이 된다. 402 Guard 는 그 검증 책임을 구매 에이전트 로컬로 옮겨 서명 직전에 실행한다.**

이건 스펙 원문으로 방어되고, "표준이 규정한 제약을 표준 주체가 없는 환경에서 실행한다"는 **인용 가능한 이름이 붙은 근거**가 된다. (⚠ 예상 반문: *"그럼 402 Guard 는 새 계층이 아니라 Credential Provider 를 구현한 것 아닙니까?"* — 답을 준비해야 한다.)

**유리한 정합 2건**: ①AP2 자율 모드가 `"the Shopping Agent MAY now sign it using its Agent Key instead of getting approval"` — 에이전트 자기 키 서명은 스펙이 명시한 모드이지 위반이 아니다. ②우리 3단계 명칭(payment-required/submitted/completed)이 공식 `google-agentic-commerce/a2a-x402` 확장과 일치한다. **축③에 쓸 수 있는 진짜 정합점.**

### 1-3. pay.sh — 필수가 아니고, 상금 수치는 미확인이다

- ★ **pay.sh 는 필수가 아니다.** 공식 심사기준 3번이 `Solana 기반 결제 연동(USDC, Solana Pay, pay.sh 등)` 으로 **'등'이 붙은 병렬 예시**다. 리포트가 인용한 `"Developers must build ... using Pay.sh"` 문장은 원출처(solanacompass)에서 **완전일치 검색으로도 재현되지 않았다.** CLAUDE.md 의 2026-07-24 판단이 재확인됐다 → **"스크리닝 탈락 가능성" 격상은 근거 없음. 원래 등급으로 되돌린다.**
- ⚠ **총상금은 미확인.** 서브에이전트는 공식 FAQ 기준 총 $5,000(1위 $3,000)라 보고했으나, 적대 검증이 같은 페이지를 열었을 때 JS 렌더 SPA 라 본문 확보에 실패했고 PRIZE 섹션이 `$0` 으로 렌더됐다. 2차 매체는 여전히 $135,000 을 붙인다. **어느 숫자도 근거로 쓰지 않는다.** (제출물에는 안 들어가므로 실무 영향은 경쟁 강도 추정뿐.)
- pay.sh 실기능(공식 문서 대조): 수취인 allowlist **없음**, 청구서 대 독립견적 대조 **없음**. 방어 수단은 allowlist 가 아니라 **사람**(`auth_required` → OS 생체인증). 에이전트 모드(`NO_DNA`/`auto_pay`)로 켜면 그 사람이 빠지고 **금액 인자 없는 불리언만** 남는다. 금액 상한은 `--help` 에서 숨겨진 실험 플래그 `--yolo-upto`(건별, CI 투입 금지 명시)뿐.
- ★ **최상급 아군 출처**: pay.sh 구독 문서가 스스로 인정한다 — 활성 구독이 **지갑을 조용히 소진**시킬 수 있으니 정기적으로 목록을 감사하라. 구독 활성화는 사용자 명령이 아니라 **유료 요청의 부수효과로 자동 발생**한다. 주최측이 만든 레일이 스스로 지목한 위험 지점이다. **인용 시 pay.sh 를 깎아내리는 톤은 금물** — "그 문서가 지목한 위험 지점에 우리가 게이트를 놓는다"로 말한다.
- ⚠ **미확인 리스크 1건**: Solana 공식 `Subscriptions & Allowances`(pre-authorize a one-time spend up to a defined cap)가 mainnet 라이브다. 샌드박스/로컬넷 가용 여부 미확인 — **가용하면 "누적 예산 상한"이 pay.sh 스택 안에서 성립해 차별점이 좁아진다.** 확인 전까지 "누적 예산 상한은 우리만의 것"이라 말하면 안 된다.

## 2. ① 카피 정정 — 재판정

### 2-1. x402 "파는 쪽 보호" — **정정 필요(단 리포트와 반대 이유)**

현행 문장이 들어간 곳: `docs/differentiation.md:34,42,58` · `docs/artifacts/pitch_deck.html:294,308,680` · `docs/artifacts/demo_script.html:308` · `docs/submission.md:41` · `docs/FEATURES.md:19` · `payments/guard.py:3`(독스트링).

**교체 권고문**(전부 스펙 원문으로 방어됨):

> x402 는 구매자의 **키**를 지킵니다. 하지만 구매자가 **무엇에 서명하는지**는 검증하지 않습니다 —
> 수취인이 합의한 상대인지, 청구액이 합의 견적과 같은지를 묻는 주체가 스펙에 없습니다.
> 그리고 `exact` 스킴은 실행되면 되돌릴 수 없는 push 결제입니다. 402 Guard 가 그 자리에 섭니다.

참고로 `pitch_deck.html:313` 의 슬라이드 2 첫 박스(*"얼마를 받았는가는 검증하지만 누구에게 보내는가를 구매자 관점에서 검증하는 항목이 없습니다"*)는 **이미 정확하다.** 마지막 문장 *"판매자 보호에 최적화된 설계입니다"* 만 과잉이다.

**예상 반문 및 답**:
- *"x402 v2 는 `amount` 인데 왜 `maxAmountRequired` 를 씁니까?"* → "v1 와이어 포맷이며 응답에 `x402Version: 1` 을 명시합니다. v2 마이그레이션은 직렬화 함수 1곳입니다."
- *"그 정도는 클라이언트 SDK 에 `if` 문 하나면 되는데 왜 '계층'이라 부릅니까?"* → **현재 두 리포트 모두 이 질문에 답이 없다. 준비 필요.**

### 2-2. AP2 표기 — **정정 필요(리포트가 맞음, 그러나 지금 코드는 더 낮춰야 함)**

★ 직접 확인: `OpenPaymentMandate._payload()`(`ap2_mandate.py:40-49`)가 서명하는 키는 **정확히 7개** — `type / user / asset / budgetTotal / perTradeMax / symbols / createdAt`. **payee 계열이 없다.**

그리고 코드 추적에서 나온 더 심각한 사실 3건:
1. `Guard.__init__`(`guard.py:103-106`)은 **mandate 서명을 검증조차 하지 않는다**(`verify()` 호출 없음). 서명 검증은 병렬 객체인 `PaymentAuthorizer.__init__` 에서만 일어난다.
2. ★ `web/engine.py:500` — `Guard(mandate, [str(broker_kp.pubkey())], ...)`. allowlist 생성 지점 **7곳 전부** 런타임에 브로커 키페어에서 만든다. 사용자 입력·mandate·설정에서 오는 곳 **0곳**. 즉 권위 원천은 **배포 운영자**다.
3. `secrets/user.json` 이 **없으면 서버가 조용히 새로 만들어 보관한다**(`_load_or_create_user_key`, `run_demo.py:52-66`). "사용자 키"의 개인키도 현재는 서버가 갖는다.

**쓸 수 없는 문장**:
- ❌ "사용자가 서명한 수취인 제약" / "위임장이 수취인을 묶는다"
- ❌ "AP2 allowed payees 를 준수한다"
- ❌ "AP2 가 pay_to 를 미검사한다"를 **프로토콜의 공백**처럼 서술하는 것 (`pitch_deck.html:318` 이 정확히 이 형태다)

**쓸 수 있는 문장**(전부 코드로 방어됨):
- ✅ "수취인 allowlist 대조를 **서명 직전에** 강제한다" → `guard.py:145`, `:224`
- ✅ "AP2 한도 검사보다 **앞에서** 통과해야 한다" → `trading_agent.py:484-486` → `:490`
- ✅ "위반이면 서명 자체가 일어나지 않아 온체인 유출 0"
- ✅ "매수·매도 **양 레그** 대칭"
- ✅ 표기: **"AP2 의 mandate 위임 모델을 솔라나 ed25519 서명으로 재구성(SD-JWT/VC 미채택)"**, 로드맵에 "SD-JWT VC 전환 시 vct·allowed_payees 채택"

> **격상 경로(선택)**: `_payload()` 에 `"payees": sorted(...)` 한 줄 + `OpenPaymentMandate.allowed_payees` 필드 + `Guard` 가 mandate 에서 목록 유도(생성자 인자는 교집합으로만 좁힘) + `mandate.verify()` 호출 추가. **공수 2~3h**(테스트·회귀 포함). 그러면 *"위임장 서명에 봉인된 수취인 제약 — 한 글자만 바꿔도 서명이 깨진다"* 를 화면에서 시연할 수 있다. 단 사용자 개인키를 서버가 보관하는 한 **"사용자 지갑이 서명한"이 아니라 "위임장에 서명으로 봉인된"까지만** 주장 가능하다.

### 2-3. 사후구제 대비 우월성 — **정정 필요(리포트가 짚은 것보다 심각)**

★ 직접 확인한 코드 사실:
- `check_delivery` 실패 시 `engine.py:1181-1206` 이 하는 일은 **4가지뿐** — `status`→`partial` 강등 / `GUARD_PENDING` emit / `auth.release()` / `pause()`. **온체인 조치 0건.**
- `release()`(`ap2_mandate.py:142-151`)는 파이썬 `Decimal` 카운터만 되돌린다. 저장소 전체에 refund/escrow/dispute 구현 **0건**.
- 결제와 배송이 **비원자적 별개 tx** 다(`broker_agent.py:250-273`) → 배송 실패 시 사용자는 **그 1건 전액**을 잃는다.

**정직하게 말할 수 있는 범위**:
> 청구서 단계에서 잡히는 실패(수취인 스왑·자산 스왑·금액 부풀리기·한도 초과·주문번호 위조)는 **서명 자체를 만들지 않으므로 손실이 0** 이고 사후 구제가 필요 없다. — 여기까지가 코드로 완전히 성립한다.

**말할 수 없는 범위**: 배송/지급 불이행까지 사전 차단이 커버한다는 주장. 그 계층은 **탐지 + 정지**이고 회수가 없다. `guard.py:20-21` 주석이 스스로 *"차단이 아니라 pending_delivery 보류 신호"* 라고 적고 있다.

**권장 표현**: *"사후 구제를 대체한다"* 가 아니라 —
> **사후 구제가 필요해지는 원인 중 '위조' 계열을 없애고, 남는 '상대방 불이행'은 (a) allowlist 로 상대를 한정하고 (b) 발생 즉시 세션을 멈춰 1건으로 상한을 씌우고 (c) `payment_tx` 서명과 빈 `delivery_tx` 를 증빙으로 남깁니다. 되돌리지는 못합니다.**
> (a)(b)(c) 는 전부 코드에 실재한다 — `guard.py:144` · `engine.py:1205` · `engine.py:1330-1336`.

**심사에서 우리가 사후 구제보다 못한 실패 모드 3가지**(먼저 말하는 편이 낫다):
1. **브로커 불이행(먹튀)** — 차지백·에스크로는 되돌리지만 우리는 못 되돌린다.
2. **allowlist 안의 배신** — `check_demand` 는 '목록에 있는가'만 본다. 우리가 막는 것은 **위조**이지 **신뢰 실패**가 아니다.
3. **표시의 정직성** — §4-1 참조.

이 상수가 `:382` 의 "402 Guard 적용 후 유출" 과 `:392` 의 **첫 화면 KPI 문구**에 그대로 찍힌다. 게다가 `:302` 가 배송 미확인 공격의 `leak`(=29.99)을 조건 없이 `:376 total_leak` 에 합산하고 두 줄 아래에 "유출 0.00" 을 출력한다 — **회수하지 못한 금액을 되찾은 것처럼 읽힌다.**

## 5. ③ API 결제 레그 — 공수와 판정

### 5-1. 재사용 가능한 것은 실제로 많다

- `payments/x402_http.py` 의 와이어 함수 8종 전부 **순수 함수**이고 도메인 값은 `accepts[0].extra` 확장 슬롯에만 들어간다 → 'API 1회 호출'을 가상 종목으로 넣어도 스펙이 안 깨진다.
- `web/broker_service.py`(233줄)가 완성된 402 자원 서버 템플릿.
- `BrokerAgent.settle()` 이 `stock_mint=None` 을 이미 안전 처리한다(`:252`, `:268`) → **'토큰 배송 없는 판매자'가 코드 수정 없이 성립**하고 이중청구·만료 방어도 따라온다.
- **`payments/guard.py` 본체는 수정 0줄** — 6개 검사 중 5개가 그대로 유효하고, 유일한 결합인 종목 검사는 `mandate.allowed_symbols` 에 가상 종목 1개를 넣으면 해소된다.

### 5-2. 그러나 공수는 19.6h 가 아니다

적대 검증이 **설계상 없으면 동작하지 않는 항목 6개가 행 자체로 누락**됐음을 적출했다:

1. ★ **결제 빈도 제어 부재** — 두뇌는 '틱×종목'마다 호출된다(`engine.py:1056`). 기본 속도 0.3초·`_bear` 481봉·3종목이면 **세션 1회 = 1,443건 결제**다. 원 명세(`differentiation.md:97` G6)는 '3틱 1회'를 못박아 뒀는데 이번 산정에 샘플링·캐싱·쿨다운이 없다. 샘플링을 넣으면 `_ai_stats` 의 `gemini_calls`/`gemini_share_pct` 정의가 흔들린다.
2. API 예산 소진 시 의미론(폴백? 정지? 판단 출처 라벨?)
3. 판매자 429 시 '정산 vs 상품 생산' 순서 설계 — 시간 배정 0
4. `run_demo.py` 배선 누락 — **devnet 증빙의 표준 경로가 CLI 인데 거기엔 레그가 안 붙는다**
5. 구매자 프로세스에서 `GEMINI_API_KEY` 를 뺀 **별도 Cloud Run 서비스**(risks 에만 언급, 시간 0)
6. 세션 단위 토글 — env 전용이면 배포본에서 켜려면 재배포해야 한다

배포·회귀 항목도 과소다. 이 저장소의 첫 Cloud Run 배포는 **배포에서만 드러난 결함 2건 + 런북 정정 4건**을 낳았다. 현행 플래그가 `--cpu 1 --max-instances 1` 인데, 구매자 워커 스레드가 같은 인스턴스의 자기 자신에게 동기 HTTP 를 걸고 그 핸들러가 다시 Gemini 를 동기 호출하는 구조를 1 vCPU 에서 검증하는 비용이 1h 에 들어갈 수 없다.

> **현실 공수: 26~34h.** (코드 분량 자체는 약 890줄로, 선례 G5 의 1,145줄을 한 세션에 낸 것을 보면 코딩 시간은 문제가 아니다. 오차는 **비코드 항목과 누락 행**에 있다.)

### 5-3. 그리고 축④ 반문의 답이 되지 못한다

- `web/server.py:81` 관례대로 메인 앱에 마운트하면 **파는 쪽과 사는 쪽이 같은 컨테이너·같은 시크릿**이다. `deploy_cloud_run.md` 는 배포본에서 `BROKER_HTTP_URL` 이 자기 자신(`127.0.0.1:8080`)을 가리키는 것을 권장 패턴으로 적어 뒀다.
- 상류 실비용이 **돈이 아니라 Gemini 무료 티어 쿼터**다(`gemini_decider.py:212-222` 의 429 쿨다운이 그 증거). *"구글에 얼마를 지불했나"* 의 답은 **0원**이다.
- 배송 검증 대응물이 없다 — `check_delivery` 는 온체인 잔액 증가분을 보는데 데이터 상품에는 잔액 델타가 없다. `BrokerAgent.settle` 은 `stock_mint=None` 이어도 `settled` 를 돌려주므로 **'결제 확정 + 상품 0 + settled'가 구조적으로 만들어진다.**
- 의도 상한이 저가에서 무력 — `_INTENT_SLIPPAGE_USDC = 0.02`(`guard.py:58`)가 고정이라 단가 0.02 USDC 면 상한이 **0.04(=200%)** 다.
- **UI 가 없어 8/3 제출물 3종 어디에도 나타나지 않는다.** (프론트 병합 충돌 위험은 사실상 0 — 파일 집합이 분리돼 있고 정적 파일은 통째 교체다. 진짜 비용은 '화면에 한 픽셀도 안 나온다'는 것.)

### 5-4. ★ 훨씬 싼 대안이 실측됐다

적대 검증 에이전트가 **읽기 전용 GET 으로 직접 실측**했다:

```bash
curl -i https://debugger.pay.sh/mpp/quote/AAPL
```
→ `HTTP 402 Payment Required` + `WWW-Authenticate: Payment`.
챌린지 디코드: `amount=10000`(0.01 USDC) · `currency=USDC 민트` · `network=localnet` · `recipient=GCH9XeHHey7nRdLMU4fsD2EVJmw87Fbmf5zCDNSXfYH9` · **`description="Stock quote: AAPL"`** · 만료 5분.

즉 **대회 공동주최 측이 운영하는 진짜 제3자 판매자**이고, 파는 물건이 하필 **우리와 같은 도메인(주식 견적)** 이다. 계정·API 키·지갑·자금이 전부 불필요하다(`--sandbox` 가 임시 지갑을 생성·자동충전). 문서상 최단 경로는 한 줄:

```bash
npx @solana/pay --sandbox curl https://debugger.pay.sh/mpp/quote/AAPL
```

- **"우리가 만들지 않은 판매자에게 결제했다"** 는 증빙이 1건 생긴다 → 축④ 반문의 실제 답.
- 챌린지에 `recipient` 와 `amount` 가 평문으로 들어 있으므로, **402 Guard 가 그 두 필드를 allowlist·의도 상한과 대조하는 그림을 pay.sh 청구서 위에서 그대로** 보여줄 수 있다 → 축③ 가점 동시 획득.
- ⚠ **주의**: 이 경로는 **MPP 프로토콜**이고 `network=localnet` 이다(`/x402/quote/AAPL` 은 403 — 원인 미확인). 우리 x402 구현과 와이어 포맷이 달라 **어댑터가 필요**하고, 기존 devnet 증빙과 다른 네트워크라 **한 화면에 섞으면 혼란**이 생긴다 — 별도 레그로 분리 제시해야 한다.

> **판정**: **8/3 전에는 유료 API 레그를 만들지 않는다.** 대신 0시간짜리 문장으로 덮는다 —
> *"구매 대상은 자체 발행 토큰이며, devnet 에 실물 토큰화 주식이 존재하지 않기 때문입니다. 민트 상수와 스왑 경로 2곳 교체로 실물 전환됩니다."*
> 만들 거라면 **8/7 파이널 통과 후 8/10~20 멘토링 기간**에 넣고, 그때도 **pay.sh 샌드박스 1건 실연동을 먼저** 검토한다(비용 대비 답으로서 훨씬 강함).

## 6. 남은 미확인 (사용자 확인 필요)

1. **디스코드 공지 원문** — pay.sh 필수 여부·제출 세부 규격·데모 영상 길이 상한. 봇 초대 링크라 도구로 열 수 없었다. **검색어 `pay.sh` 로 공지 채널을 훑는 것이 남은 최저비용 확인.**
2. **총상금** — 공식 페이지가 JS 렌더라 확보 실패. FAQ($5,000) vs 2차 매체($135,000) 27배 충돌. **브라우저로 직접 확인 필요.**
3. **Solana Subscriptions & Allowances 의 샌드박스 가용 여부** — 가용하면 "누적 예산 상한" 차별점이 좁아진다. **확인 우선순위 높음.**
4. **참가 규모·본선 진출 팀 수** — 파이널리스트 약 10팀은 확인됐으나 모수 미확인. 리스크 강도 전체가 여기 종속.
5. `debugger.pay.sh/x402/quote/AAPL` 이 403 인 이유 — MPP 만 열려 있는지, 헤더가 필요한지.
6. x402 거버넌스 이관 — FAQ 하단이 `x402-foundation/x402` 를 가리키는데 우리가 조사한 정본은 `coinbase/x402`. **출처 표기에 영향.**
