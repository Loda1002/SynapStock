# B안 — 자체 Solana 온체인 프로그램 (미래 작업 기록)

> **상태**: 기록만. **설계·구현 착수 안 함.** 2026-07-29 작성.
> 8/3 제출 마감과 무관하다. 나중에 판단할 수 있을 만큼만 남긴다.
> A안(SPL 위임) 분석은 [`onchain_budget_rfc.md`](onchain_budget_rfc.md).

## 1. 무엇을 체인에 올리는가

402 Guard 의 서명 직전 검사 8종 중, **상대방 응답과 무관하게 사전에 고정할 수 있는 것**만
프로그램의 위임장 계정(PDA)에 넣고 실행 시 검증한다.

| 검사 | 체인으로 | 사유 |
|---|---|---|
| 총 예산 상한 | ✅ | A안이 SPL 위임으로 이미 하는 것. 프로그램이면 **순투입/누적을 우리가 정의**할 수 있다(A안의 §3 난점이 사라진다) |
| **수취인 allowlist** | ✅ | **B의 핵심.** A안이 못 하는 것. AgentFabric 에도 없다 |
| 허용 종목(민트) | ✅ | 자산 바꿔치기를 체인이 거절 |
| 건별 한도 | ✅ | 계정 필드 하나 |
| **만료 시각** | ✅ | `OpenPaymentMandate` 에 만료 필드가 아예 없는 갭(벤치마크 §4-4)을 동시에 닫는다 |
| 주문번호 형식·Memo 대사 | ❌ | 체인이 볼 이유가 없다. 오프체인 유지 |
| 청구서 의미 대조(LLM) | ❌ | 구조적으로 불가. 오프체인 유지 |
| 배송 확인 | ❌ | 정산 후 검사. 오프체인 유지 |

**결과 주장**: *"금액·수취인·종목·만료를 체인이 강제한다."*
AgentFabric 의 온체인 세션키는 **호출 대상·셀렉터·시간창** 3가지만 강제하고 금액·수취인은
자기 소스에 `NOT enforced on-chain` 이라 적혀 있다(`docs/reports/agentfabric_benchmark.md §1`).
→ **B가 완성되면 1위 수상작이 못 한 것을 하는 셈이 된다.**

## 2. 대략의 규모 `[추정 — 실측 아님]`

| 항목 | 규모 |
|---|---|
| Anchor 프로그램 | 200~400줄 (계정 2개: `Mandate` PDA, `Vault` 토큰계정 / instruction 4개: `create_mandate` · `spend` · `revoke` · `close`) |
| 클라이언트 (Python) | 150~250줄 — Anchor IDL 없이 수동 instruction 인코딩이 현실적(파이썬 Anchor 생태계가 약하다) |
| 프로그램 테스트 | TypeScript(anchor test)가 표준. 저장소에 Node 가 **미설치**라 이것부터 걸린다 |
| 앱 배선 | A안의 C4·C5·C7 과 **동일**(RFC §8-1) |
| **합계** | **30~50h**, Anchor 미경험 전제. 벤치마크 §6 의 40h 추정과 대체로 일치 |

## 3. 필요한 도구·학습

- **Rust + Anchor 툴체인** — 현재 저장소 Rust **0줄**.
- **Node.js** — `anchor test` 표준 경로에 필요한데 **이 PC에 미설치**로 확인돼 있다
  (메모리 `autotrader-dev-env-windows`). 설치가 선행 과제.
- **Solana 프로그램 배포** — devnet 프로그램 배포에 SOL 약 2~5 필요 `[추정]`. 파우셋 제약과
  겹친다.
- **PDA·CPI 개념** — 프로그램이 Vault 토큰계정의 authority 가 되어 `transfer_checked` 를
  CPI 로 호출하는 구조.

## 4. 예상 위험

1. **감사받지 않은 컨트랙트가 자금을 쥔다.** A안은 Solana 가 이미 검증한 SPL Token 프로그램을
   쓰지만, B는 우리가 쓴 코드가 Vault 를 소유한다. 버그 = 전액 손실. 심사장에서
   *"이 컨트랙트는 누가 감사했나요"* 는 나올 수 있는 질문이다.
2. **x402 와의 정합.** 지금 결제 tx 는 순수 SPL `TransferChecked` 라 판매자가
   `verify_payment` 로 구조 검증한다(`payments/x402_solana.py:197`). B에서는 우리 프로그램의
   CPI 를 거치므로 **명령 구조가 바뀌어 판매자측 검증을 같이 고쳐야 한다** — A안은 이게
   불필요했다(RFC §2-3 실측). **B에서 새로 생기는 비용이다.**
3. **범용성 상실.** 제3자 판매자는 우리 프로그램을 모른다. 표준 x402 결제가 아니게 되면
   "누구와도 결제한다"는 서사가 약해진다.
4. **일정.** 8/10~20 멘토링 구간은 10일이고 8/21 데모데이가 붙어 있다. 30~50h 를 그 안에
   넣으면서 데모를 안정적으로 유지하는 것은 위험하다.

## 5. 언제가 적기인가

**8/7 파이널리스트 통과 후, 8/10~20 멘토링 구간.** 근거:

- 8/3 1차 심사는 소개서·저장소·영상 3종만 본다 → B가 있어도 볼 사람이 없다.
- 8/3 전에 넣으면 화면이 바뀌어 **영상을 다시 찍어야 한다**.
- 멘토링 구간은 "계속 만들 팀"을 보여주는 자리다. AgentFabric 의 상금이 일시금이 아니라
  9개월 인큐베이션이었다는 사실(벤치마크 §4-7)이 심사진의 선호를 시사한다 `[추정]`.

**선행 조건**: ① A안 C1~C5 완료(구조 반전이 끝나 있어야 한다 — RFC §8) ② Node.js 설치
③ devnet SOL 확보.

## 6. A와의 관계 (요약)

- A의 구조 변경 **약 80% 가 B에서 재사용**된다. 두 번 고치는 것은 `payments/delegation.py`
  한 파일 정도. 상세 근거는 RFC §8.
- **A는 B의 축소판이 아니다.** A는 금액 축 하나만, B는 수취인·종목·만료까지.
- 따라서 A를 했다고 402 Guard 가 필요 없어지지 않고, B를 해도 청구서 의미 대조는 오프체인에 남는다.
