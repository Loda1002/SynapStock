## 1. A안 정의와 현재 구조

**현재** — 에이전트가 자기 지갑에 USDC 를 들고, 자기 키로 직접 전송한다.

| 항목 | 위치 |
|---|---|
| 출금 계정을 지불자에서 유도 | `payments/x402_solana.py:99` `src_ata = get_associated_token_address(payer.pubkey(), mint)` |
| 전송 권한 = 지불자 본인 | `payments/x402_solana.py:118` `owner=payer.pubkey()` |

### 2-1. 확인된 동작 `[실측]`

| # | 질문 | 실측 결과 |
|---|---|---|
| 1 | delegate 가 서명자일 때 `transfer_checked` 의 authority 자리 | **계정 순서가 동일하다.** `owner=` 자리에 소유자 대신 delegate 를 넣고 delegate 가 단독 서명하면 통과. 소유자 서명 불필요 |
| 2 | `delegated_amount` 가 전송마다 깎이는가 | **깎인다.** 한도 25 → 10 전송 → `delegatedAmount` 15로 자동 감소 |
| 3 | 0 이 되면 어떻게 되는가 | **`delegate` 필드 자체가 `None` 으로 해제된다.** 잔여 15를 정확히 소진하자 `{'delegate': None, 'delegatedAmount': None}` |
| 4 | 한도 초과 시 거절 에러 | `custom program error: **0x1**` (`insufficient funds`) — **preflight 시뮬레이션에서 거절**되어 트랜잭션이 체인에 올라가지 않는다(수수료 0, 서명 미기록) |
| 5 | 소진 후 전송 | `custom program error: **0x4**` (`owner does not match`) — 4번과 다른 코드 |
| 6 | 재충전(추가 approve) | 가능. **단 누적이 아니라 덮어쓰기다.** 잔여 15인 상태에서 `approve(10)` → 10 (25가 아님) |
| 7 | 회수(`revoke`) | 즉시 `delegate=None`, 이후 에이전트 전송은 `0x4` 로 거절 |
| 8 | 에이전트가 스스로 한도를 올릴 수 있는가 | **불가.** 에이전트가 자기를 owner 로 넣어 `approve` 시도 → `0x4`. **상한은 소유자만 바꾼다** |
| 9 | 위임 중 소유자 본인의 사용 | 자유롭게 가능하고, **소유자 전송은 `delegatedAmount` 를 깎지 않는다** |

### 2-2. ⚠ 실측이 드러낸 함정 2건

**(a) 한도 초과와 잔액 부족이 같은 에러 코드다** `[실측 — 대조군 실험]`

한도를 잔액보다 크게 올린 뒤 잔액 초과 전송을 시도해 대조했다. 둘 다 `0x1` 이다.

| 상황 | 에러 |
|---|---|
| 한도 초과 (잔액은 충분) | `custom program error: 0x1` |
| 잔액 부족 (한도는 충분) | `custom program error: 0x1` |
| 한도 소진 후 (delegate 해제됨) | `custom program error: 0x4` |
| revoke 후 | `custom program error: 0x4` |

→ **에러 코드만으로 "한도 거부"를 표시할 수 없다.** 화면에 `GUARD_ONCHAIN_LIMIT` 같은 라벨을
붙이려면 실패 직후 `delegatedAmount` 와 `amount` 를 각각 읽어 어느 쪽이 모자랐는지 판별해야
한다(RPC 1회 추가). 이걸 빠뜨리면 잔액이 빈 것을 "체인이 한도를 집행했다"고 잘못 광고하게 된다.

**(b) 거부가 재시도 백오프를 타지 않는다 — 다행** `[실측]`

`payments/x402_solana.py:263 rpc_retry` 는 일시적 오류를 6회·지수 백오프(최대 62초)로 재시도한다.
한도 거부가 여기 걸리면 틱마다 1분씩 멈춘다. 실제 거부 예외를 우리 `submit_and_confirm` 에
그대로 통과시켜 측정했다:

```
submit_and_confirm 소요: 0.04초
예외 타입 : RPCException  (module=solana.rpc.core)
_is_transient        = False
>>> 재시도 루프를 탔는가: 아니오
```

즉시 실패한다. **단 `except` 가 없는 경로라 예외가 그대로 위로 던져진다** — `_buy_cycle` 의
`try` 블록에는 `except` 가 없고 `finally` 만 있다(`web/engine.py:1241-1299` `[코드]`). 배선 시
이 예외를 잡아 `GUARD_*` 로 표면화하지 않으면 **틱 루프가 예외로 죽는다.**

### 2-3. 브로커측 검증은 그대로 통과한다 `[실측 — 오프라인]`

A안 모양의 tx(출처 = 사용자 ATA, 서명·수수료 = 에이전트)를 만들어 브로커의 실제 검증 함수에 넣었다.

```
[브로커] verify_payment  -> ok=True  reason=검증 통과  amount=12340000
```

`verify_payment` 는 민트·수취 ATA·금액·Memo 만 보고 **출처 ATA 는 아예 보지 않는다**
(`payments/x402_solana.py:197-225` `[코드]`). 판매자측 코드 변경은 필요 없다.

다만 부수 효과가 하나 있다 — 브로커는 **수수료 지불자를 구매자로 간주한다.**

```
account_keys[0] = agent (user 아님)
```

`agents/broker_agent.py:244-245` 주석 그대로 *"결제 트랜잭션의 fee payer == 구매자"* 이고,
매도 레그도 `:166 seller_pubkey = tx.message.account_keys[0]` 다 `[코드]`.
→ **주식은 계속 에이전트 지갑으로 배송되고, 매도 대금도 계속 에이전트 지갑으로 들어온다.**
A안에서 이건 버그가 아니라 오히려 §3의 해법이 성립하는 이유다. 단 저 주석은 거짓이 된다
("fee payer == 구매자" → "fee payer == 위임받은 실행자").

### 2-4. 현행 함수는 그대로 못 쓴다 `[실측]`

```
현행 build_transfer_transaction 의 source ATA = agent ATA
>>> 그대로 재사용 가능한가: 아니오 (source_owner 인자 추가 필요)
```

`payments/x402_solana.py:99` 가 출처를 지불자에서 유도하므로, **`source_owner` 선택 인자 추가**가

## 3. ★ 결정적 발견 — 누적 상한 vs 순투입 한도

**이것이 A안의 실제 난점이고, PoC 이전에는 안 보이던 것이다.**

- **SPL 위임 = 누적 총 유출 상한.** 단조 감소만 한다. 판 돈이 돌아와도 `delegatedAmount` 는
  회복되지 않는다(§2-1 #9: 소유자 입금은 위임량과 무관).
- **우리 예산 = 순투입 한도.** `credit_sale()` 이 매도 대금만큼 `spent_usdc` 를 되돌린다
  (`payments/ap2_mandate.py:157-173`, 독스트링이 *"예산(budget_total)은 '순투입 한도'로 해석한다"*
  라고 명시) `[코드]`.

### 3-1. 얼마나 벌어지는가 `[실측]`

대표 데모 설정(TSLA 하락장·추세추종·예산 100 USDC)으로 백테스트를 돌려 누적 매수액을 합산했다.

```bash
python scripts/backtest.py --symbol TSLA --suffix _bear --strategy trend --trend-signal pxma20 --max-bars 481 --budget 100
```

| 전략 | 예산 | 매수 건수 | **누적 매수 총액** | 배수 | 최대 1건 |
|---|---|---|---|---|---|
| 추세추종 `pxma20` (올인/올아웃) | 100 | 21 | **2,394.80 USDC** | **23.9×** | 172.60 |
| 조건형 `gemini-strict` (건당 30) | 100 | 68 | **1,737.12 USDC** | **17.4×** | 30.00 |

→ **`approve(예산 100)` 을 그대로 걸면 추세추종은 첫 매수(99.99) 직후 한도가 0.01 이 되어
두 번째 매수부터 전부 거절된다.** 데모가 1거래로 끝난다. "온체인 예산 집행"을 소박하게 붙이면
제품이 멈춘다.

### 3-2. 해법 — 자금 출처를 나눈다

**재활용 자금은 에이전트 지갑, 신규 투입만 사용자 위임 계정에서 끌어온다.**

```
매수: 에이전트 지갑에 잔액이 충분하면 거기서 (위임량 무소모)
      부족하면 사용자 위임 ATA 에서      (위임량 차감 ← 여기만 체인이 집행)
매도: 대금은 에이전트 지갑으로 (§2-3 — 코드 변경 없이 이미 그렇게 된다)
```

이러면 **`delegatedAmount` ≈ AP2 `remaining_usdc`** 가 되어 두 계층이 같은 것을 센다.
위 추세추종 세션에 대입하면 위임 소모는 첫 진입 99.99 **한 번뿐**이고, 나머지 20건은 전부
매도 대금 재투자라 에이전트 지갑에서 나간다 `[추정 — 시뮬레이션 미실행]`.

**정직한 경계선(반드시 문서·화면에 함께 적을 것)**:
체인이 강제하는 것은 **사용자 지갑에서 나가는 순투입 총액**이다. 시장에서 번 돈은 에이전트
지갑에 있고 그건 402 Guard(오프체인)만 지킨다. 그래도 **현행보다는 엄격하다** — 지금은
초기 자본까지 전부 에이전트 지갑에 있다.

⚠ 한 가지 구현 제약: 한 결제를 두 출처에서 쪼개 낼 수 없다. `verify_payment` 는 첫 번째
`TransferChecked` 를 찾아 금액이 **정확히** 일치해야 통과하므로(`x402_solana.py:203,219` `[코드]`)
분할 전송은 판매자측 검증에서 떨어진다. → "출처는 건당 하나" 규칙이 필요하고, 경계값
(에이전트 잔액이 결제액보다 조금 모자란 경우) 처리를 정해야 한다 `[추정]`.

## 4. 얻는 이득

### 4-1. 위협 모델 — 무엇이 실제로 좋아지는가

| 공격자 | 현재 | A안 이후 |
|---|---|---|
| 악성 브로커 (가짜 청구서) | 402 Guard 가 차단 | **변화 없음** — Guard 가 계속 담당 |
| **에이전트 키 탈취 / 엔진 버그** | **지갑 잔액 전부 유출** | **위임 잔량까지만.** 사용자 원금 나머지는 체인이 지킨다 |
| 에이전트가 스스로 한도 상향 | 파이썬 객체라 코드만 고치면 가능 | **불가** — 소유자 서명 없이는 `approve` 거절 `[실측 §2-1 #8]` |
| 사용자의 즉시 회수 | 없음(엔진 정지에 의존) | **`revoke` 1건으로 즉시 차단** `[실측]` |
| **서버 전체 장악** | 전부 유출 | **여전히 전부 유출** — 데모는 `user.json` 도 같은 Cloud Run 시크릿이다(`docs/deploy_cloud_run.md:76`) `[코드]` |

**A 이후에도 체인이 못 보는 것 (402 Guard 가 계속 필요한 이유)**:
수취인 · 자산 종류 · 종목 · 청구서 의미 · 건별 한도 · 의도 지출 상한 · 배송 확인.
SPL 위임이 강제하는 것은 **"그 ATA에서, 그 민트를, 누적 얼마까지"** 단 하나다.
**A는 B의 축소판이 아니라 '금액 축' 하나다.**

### 4-2. 심사 4축 기여 `[추정]`

- **축③(기술 완성도·블록체인 인프라 연동)** — 기여가 가장 크다. CLAUDE.md 최신 분석이
  *"축③이 주축인 장면이 3분 영상에 0초"* 라고 적고 있고, `approve` 트랜잭션은 explorer 에서
  한 줄로 보이며 심사위원이 직접 재현할 수 있다.
- **축①(혁신성·UX)** — 서사가 바뀐다. "에이전트 지갑에 돈을 옮겨 준다"(맡긴다) →
  **"내 지갑에서 정해진 만큼만 끌어 쓴다"**(꺼내 쓰게 한다). 후자가 자율성 인에이블러 문법
  (`agentfabric_benchmark.md §5`)에 정확히 맞는다.
- **축②(AI 활용)** — 기여 없음.
- **축④(실제 구동)** — 라이브 devnet 세션이 성사될 때만. 현재 배포본은 `ALLOW_LIVE_FROM_WEB=0`
  이고 기록된 세션 12/12가 전부 dry 다 → **드라이런 촬영본에는 아무것도 안 보인다.**

### 4-3. AgentFabric 대조가 뒤집힌다

1위 수상작은 자기 소스에 `Advisory limits (NOT enforced on-chain, just for UI display)` /
`Budgets CANNOT be enforced on-chain` 이라고 적어 두었다(`agentfabric_benchmark.md §1`).

## 8. ★ 반드시 답할 질문 — A → B 순서인가, 독립인가

**답: 대체로 A → B 가 유리하다. A에서 하는 구조 변경의 대부분이 B에서 그대로 재사용된다.**

### 8-1. 재사용되는 것 (A 공수의 약 80% `[추정]`)

A와 B는 **같은 구조 반전**을 요구한다 — *"에이전트가 자금을 소유하지 않는다."*
출처가 A에서는 사용자 ATA(위임), B에서는 프로그램 PDA 계정(또는 PDA에 위임된 사용자 ATA)일
뿐, 그 위의 코드는 동일하다.

| A에서 한 일 | B에서 |
|---|---|
| C1 `source_owner` 인자 (출처를 지불자에서 분리) | **그대로 필요** |
| C4 출처 선택 · 거부 예외 처리 · state 필드 | **그대로 필요** (에러만 커스텀으로 교체) |
| C5 교차검증·스냅샷 3지갑 확장 | **그대로 필요** |
| C7 화면(온체인 잔량 표시) | **그대로** (읽는 대상만 PDA로) |
| C8 문서·서사 재작성 | **그대로** |
| §3-2 자금 흐름 설계(재활용은 어디로, 신규는 어디서) | **그대로** — 이게 제일 어려운 부분이고 B에서도 똑같이 필요하다 |

### 8-2. 버려지는 것 (A 공수의 약 20% `[추정]`)

- C2 의 `approve_checked`/`revoke` 호출 → 프로그램 instruction 으로 교체.
- §2-2a 의 에러 판별 로직 → **Anchor 커스텀 에러가 애초에 모호하지 않아 불필요해진다**(개선).

**즉 두 번 고치는 부분은 `payments/delegation.py` 한 파일(1.5h)뿐이다.**

### 8-3. A 를 먼저 하면 B 가 쉬워지는가 — 그렇다

A는 **Rust 없이** 다음 질문들을 강제로 답하게 만든다:
매도 대금은 어디로 가는가 · 재활용 자금과 신규 투입을 어떻게 구분하는가 · 교차검증은 두 지갑을
어떻게 합산하는가 · 드라이런은 무엇을 보여주는가 · 한도 거부를 화면에 뭐라고 쓰는가.
이 답들이 전부 B로 이월된다. B로 직행하면 **이 설계 문제와 Anchor 학습을 동시에** 풀어야 하고,
실패했을 때 원인이 설계인지 체인 코드인지 분리가 안 된다.

### 8-4. B 직행 평가

**조건부로만 합리적이다.** B 직행이 나은 유일한 경우는 *"A를 어차피 최종 산출물로 안 쓸 것이고
3주 이상이 있다"* 인데, 8/10~20 멘토링 구간은 10일이고 8/21 데모데이가 붙어 있다.
저장소에 Rust 0줄, Anchor 경험 0 → **B 직행은 그 창에서 위험이 크다** `[추정]`.

### 8-5. ⚠ 단, A와 B는 같은 주장이 아니다

A는 **"얼마가 내 지갑을 떠나는가"** 하나만 강제한다.
B는 **"누구에게 · 무엇에 대해 · 언제까지"** 를 강제한다.
A 이후에도 유효한 위임장을 쥔 공격자는 **위임 잔량 전액을 임의 주소로 보낼 수 있다.**
→ A는 B의 부분집합이 아니라 **다른 축**이고, 402 Guard 는 A 이후에도 그대로 필요하다.
소개서·발표에서 A를 "온체인 가드"라고 부르면 과장이다. 정확한 표현은
**"예산 상한만 체인으로 내렸습니다. 나머지 7가지 검사는 여전히 서명 직전 오프체인입니다."**
