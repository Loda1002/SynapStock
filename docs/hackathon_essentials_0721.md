## 2. 결제 스택 선택지 (Q&A로 확정된 규칙)

- 필수는 "결제 레이어 = 솔라나" 하나뿐. 그 위 구현은 자유:
  - **pay.sh** — GCP×솔라나 재단의 에이전트용 API 결제 게이트웨이. 가입·API키 없이 유료 API 호출, 쓴 만큼 USDC 실시간 정산. **x402·MPP 동시 지원. Claude/Codex 등 CLI 에이전트 전부 지원.** 로컬넷 없이 **샌드박스 모드**로 테스트 가능
  - **x402** — 커뮤니티 주도(리눅스 파운데이션). Facilitator가 온체인 거래를 대신 완료해 주는 머신 페이먼트 프로토콜
  - **Solana Pay** — 허용
  - **자체 스마트 컨트랙트** — 허용 ("자체적으로 구현하셔도 크게 문제 없습니다")
- 프로토콜 계층 참고: A2A(에이전트↔에이전트) / MCP(에이전트↔툴) / AP2(mandate 기반 결제 위임) / UCP(A2A+AP2 통합) / x402·MPP(정산 레일). **AP2 안에서 x402를 결제 레일로 쓸 수 있음** → 우리 아키텍처(A2A 협의 + AP2 한도 + x402 정산)와 정확히 일치
- pay.sh 보안 구조: 개인 키를 에이전트에 주지 않고, 유료 엔드포인트 도달 시 사람 생체인증 승인 필요 → 프롬프트 인젝션 완화 (소개서 보안 섹션에 인용 가능)

## 3. 네트워크·퍼셋 실무

- 개발 순서: **Localnet(개발의 99%) → Devnet(외부 접속·시연·제출) → Mainnet은 쓰지 않음**
- Testnet은 솔라나 클라이언트 개발자용 — 우리와 무관
- Devnet SOL 퍼셋: 하루 0.5~5 SOL 제한, 공개 퍼셋은 어뷰징 때문에 받기 어려움(발표자도 실패)
- **→ 액션: 디스코드 솔라나 채널(전용 티켓 채널 개설 예정)에 Devnet SOL을 지금 미리 요청.** 마감 직전 요청 피할 것. 원하는 만큼 지급해 준다고 공언함
- 자체 테스트 토큰은 무한 발행 가능 → 온체인 자산(토큰화 주식 등)은 토큰 발행으로 해결

## 4. 계정·크레딧 실무

- 참가·크레딧에는 **개인 Gmail 필수** (학교/회사 워크스페이스 계정 제한 가능)
- GCP $300 크레딧은 **신규 계정에만** 지급
- **$300 크레딧으로 Gemini API 결제 불가** (별개 시스템) → Gemini API는 **자체 무료 티어** 사용
- Gemini 무료 티어 초과가 예상되면 **디스코드에 사전 문의** → 추가 크레딧 검토해 줌

## 5. 전략 인사이트 (수상 확률을 높이는 요소)

- **당위성이 수상을 가른다** (유준혁·김채린 공통 강조). 답해야 할 질문:
  - 왜 카드망이 아닌 블록체인인가? (카드망도 예치+배치 정산으로 마이크로페이먼트 흉내 가능 → 진짜 차별점: 인증·로그인 없는 결제, 낮은 수수료, 빠른 속도, 24/7 국경 무관, 에이전트가 계좌 개설 불가하지만 지갑은 코드 한 줄)
  - 왜 결제가 이미 편한 한국에서 AI 에이전트로 이걸 혁신해야 하는가?
- 유망 레이어: **커머스&체크아웃 / 신원&의도 증명 / 검증&가드레일** (우리 프로젝트는 AP2 한도·검증 = 가드레일 레이어에 강점)
- 에이전트 개입 3단계 중 **위임~완전 자율** 구간이 이 해커톤의 본령 (사람 개입 없는 자율 결제를 보고 싶다고 명시)
- 시장 조사: x402scan.io / mppscan.io / pay.sh 카탈로그에서 실제 팔리는 엔드포인트 확인. 현재는 토큰 런치보다 **데이터 서비스**가 주목받는 흐름
- 레퍼런스: 솔라나 콜로세움 수상작(AI 에이전트 3팀, 예: flovia 402), Cloudflare Monetization Gateway(x402 기반 에이전트 과금), AWS 유사 상품
- 기존 오픈소스 확장 참여 OK — 단 무엇을 새로 해결했는지 명시

## 6. 데모 세션 플로우 → Claude 개발 연동 매핑

황선화 SA의 데모는 "Stitch → Antigravity(Gemini) → GCP 배포" 파이프라인. 각 단계를 Claude 중심 워크플로로 이렇게 치환한다. **핵심 원칙: 개발 도구는 Claude, 프로덕트 런타임의 AI(판단·대화)는 Gemini API — 심사 2번 축(AI 활용도)은 런타임 Gemini로 충족.**

| 데모 단계 (Gemini 생태계) | Claude 워크플로 치환 | 연동 포인트 |
|---|---|---|
| Stitch로 자연어 디자인 | Stitch는 무료 독립 툴이므로 **그대로 사용** | 디자인 에셋을 zip으로 다운로드해 Claude 세션에 업로드하거나, Stitch API 키 발급(계정→설정→API key) 후 **Stitch MCP를 Claude에 연결** — MCP는 표준이라 Antigravity 전용이 아님 |
| Stitch MCP → design.md 생성 | Claude가 디자인 에셋을 읽고 `design.md` 생성 | 동일 산출물, 도구만 교체 |
| /grill-me (요구사항 인터뷰) | Claude에게 "구현 전에 요구사항을 인터뷰로 구체화해 달라"고 요청 (Cowork에선 AskUserQuestion, Claude Code에선 plan mode가 같은 역할) | 서버사이드 아키텍처, 데이터 폴백 정책 등 3~4개 질문에 답하는 패턴 동일 |
| Implementation plan 작성·승인 | Claude plan mode / 계획서 작성 후 승인받고 진행 | 동일 |
| 서브에이전트 병렬 구축 (프론트/백엔드/결제) | Claude 서브에이전트(Agent tool)·워크플로로 병렬 개발 | 동일 개념 |
| Firestore(상품·재고) | 동일하게 Firestore 사용 — Claude가 코드 작성, 인증은 gcloud CLI/서비스 계정 | GCP는 개발 도구와 무관 |
| pay.sh 샌드박스 결제 연동 | **Claude 공식 지원 확인됨** — pay.sh 클라이언트 한 줄 연동, 샌드박스 모드로 테스트 | Q&A: "codex든 클로드든 모두 pay.sh 게이트웨이를 호출할 수 있습니다" |
| Cloud Run 배포 (Dockerfile 자동 생성) | Claude가 Dockerfile 작성 → `gcloud run deploy` | 동일 |
| 배포 후 검증 (재고 감소를 UI+DB 양쪽 확인) | 동일한 검증 절차를 Claude 체크리스트로 수행 | §7 검증 루틴 참고 |
| 제품 내 AI 어시스턴트 = Gemini 3.5 Flash | **여기만 Gemini 유지** — 런타임 대화·판단은 Gemini API(무료 티어) 호출 | 심사 기준 "Gemini를 비롯한 AI 활용도" 충족. 우리 코드의 "규칙 기반 매매 판단 → Gemini 교체 지점"이 바로 이 자리 |

### 연동 시 유의

- Antigravity 전용 기능(Scheduled tasks, 터보 모드 등)은 치환 불필요 — 데모 편의 기능일 뿐 제출물과 무관
- Antigravity/Gemini로 개발하지 않아도 **가산점 손해 없음** (Q&A 확정)
- Stitch MCP를 붙일 수 없는 상황이면 zip 익스포트 → 업로드로 충분 (디자인은 심사 4축 중 UX에만 영향)
- Codelabs(Antigravity·Stitch 실습)는 참고용 — 우리 파이프라인에서는 필수 아님

## 7. 데모에서 배운 검증 루틴 (우리 프로젝트에 이식)

발표자가 보여준 검증 패턴을 그대로 채택:

1. 로컬에서 결제 전 과정 실행 → 영수증 확인
2. **상태 변화를 양쪽에서 검증** (데모: 재고 32→31을 화면과 Firestore 모두 확인 / 우리: 포지션·잔액 변화를 앱 상태와 온체인 조회 모두 확인)
3. 배포 후 배포 URL에서 동일 검증 반복
4. 심사용으로 **트랜잭션 해시·실행 로그를 파일로 남김** (심사 4번 축)

## 8. 우리 프로젝트(자율 주식매매 멀티에이전트)에 주는 시사점

- 트랙 적합: Multi-Agent Commerce + Autonomous On-chain Settlement 조합 — 4가지 출발점은 조합 가능이라고 명시됨
- 아키텍처(A2A 협의 + AP2 한도 + x402 정산)는 세션에서 설명된 표준 계층 구조와 정확히 일치 — 소개서에서 이 정합성을 명시하면 설득력 상승
- 당위성 논리 보강: "에이전트는 증권 계좌를 개설할 수 없지만 지갑은 가질 수 있다 / 24/7 시장 / 한도는 AP2 mandate로 온체인 강제" — 김채린 세션의 3요소 논리와 연결
- 사람 개입 없는 자율 결제(주최 측 최우선 관심사)가 이미 우리 설계의 핵심
- 할 일 추가: ① Devnet SOL 디스코드 선요청 ② pay.sh 샌드박스 검토(현행 x402 직접 구현과 비교 후 채택 여부 결정 — 둘 다 허용이므로 전환 의무 없음) ③ 트랜잭션 로그 아카이빙 체계
