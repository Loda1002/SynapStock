### 1.2 권장 설계 — "한 번 받아서 재생(replay)" + 선택적 라이브

```
scripts/fetch_market_data.py   # 1회 실행: Alpha Vantage/Alpaca → data/market/{SYMBOL}_{interval}.csv 저장
market/price_feed.py
  ├ MockPriceFeed      (기존, 규칙 트리거 데모용 — 유지)
  ├ ReplayPriceFeed    (신규, 실데이터 CSV를 순서대로 재생 · 배속·시작지점 지정)
  └ AlpacaPriceFeed    (선택, 라이브 조회 — 실패 시 Replay로 폴백)
```

**왜 리플레이가 기본인가**: ①데모데이 오프라인 폴백 원칙(네트워크 없이도 시연 가능) ②결정적 재현 — 심사·영상 촬영 때 같은 구간이 같게 흐름 ③Gemini 판단 비교 실험에서 조건 통제 가능 ④무료 API 한도(25콜/일)에 런타임이 묶이지 않음.

**결정 필요(사용자)**:
- (a) 종목·기간·간격: 예) AAPL·TSLA·NVDA 일봉 2년치 / 또는 1분봉 최근 며칠 → **변동성 있는 구간**을 고르는 게 판단 검증에 유리
- (b) 데이터 파일을 **저장소에 커밋할지**(재현성 ↑, 데이터 재배포 약관 확인 필요) vs **`data/`를 gitignore 하고 README에 fetch 안내**(안전, 대신 심사자가 키 필요) → 절충안: 소량 샘플만 커밋 + 전체는 스크립트
- (c) 틱 ↔ 봉 매핑: 지금은 "2틱 = 캔들 1개"인데 실데이터에서는 **1틱 = 1봉**이 자연스럽다 → `TICKS_PER_CANDLE` 제거/조정

### 1.3 실데이터 도입 시 함께 손봐야 하는 것 (놓치기 쉬움)

1. **매매 규칙 기본값**: 현재 `buy_below=178 / sell_above=185`는 목 시세(기준가 180) 전용. 실제 종목 가격대에 맞춰 재설정하거나, **비율 기준(예: 5일 이동평균 대비 −2%)**으로 바꿔야 함 → §2와 함께 설계
2. **예산·건별 한도 스케일**: 종목가가 400 USDC면 100 USDC 예산으로는 1주도 못 삼 → 소수점 매수(현재 지원) 유지 + 기본 예산 재검토
3. **캔들 집계·차트 축**: 일봉이면 x축 라벨을 날짜로, 세션 시작가 대비 등락 → "전일 종가 대비"로
4. **데모 시나리오 재설계**: 지금 데모는 "틱 7에 매도기준 돌파"라는 목 시세 설계에 의존. 실데이터에서는 **매수·매도·AP2 거부가 모두 나오는 구간을 골라 고정**해야 영상 촬영이 안정적
5. **API 키 관리**: `.env` → 배포 시 Secret Manager (지갑키와 동일 경로)

## 2. Gemini 매수·매도 프로토콜 검증 (사용자 우선순위 2)

목표: "**AI가 실제로 판단해서 사고팔고, 그게 온체인 결제로 이어진다**"를 실데이터 위에서 증명. (심사 4축 중 ②AI 활용도 + ④실제 구동)

### 2.1 판단 품질을 올리는 축 (`docs/user_feedback_p2.md` "매매 기준" 절과 통합)

- **입력 보강**: 프롬프트에 현재 가격만이 아니라 **MA5·MA20, 최근 N봉 등락률, 변동성, 보유 평단 대비 손익률**을 넣는다 (이미 화면에서 계산 중 — 서버에서 같이 넘기면 됨)
- **재량 허용**: 현재 프롬프트는 "규칙 위반 판단 금지"라 재량이 0. → **한도는 AP2가 기계적으로 차단(변경 없음)**, 판단은 "추세 근거로 매수/매도 **보류** 가능"까지 허용. 심사 서사의 경계("한도=기계, 판단=AI")를 그대로 유지
- **모드 토글**: 엄격 모드(규칙 그대로) / 추세 모드(재량 허용) — UI 셀렉트, 세션 단위 고정
- **세션 내 회고**: 직전 판단과 그 결과(체결가·이후 가격)를 프롬프트에 짧게 넣어 "학습처럼" 보이게. 파인튜닝은 범위 밖

### 2.2 검증 방법 — 백테스트 러너 신설

```
scripts/backtest.py --symbol AAPL --from 2025-01-02 --to 2025-03-31 --brain gemini|rule --mode strict|trend
→ 리플레이 피드로 빠르게 돌려서: 총손익 · 수익률 · 승률 · 최대낙폭(MDD) · 매매횟수 · AP2 거부 · 판단 출처 분포
```
- **규칙 vs Gemini(엄격) vs Gemini(추세)** 3종을 같은 구간에서 비교 → 소개서에 넣을 근거 숫자 확보
- **주의: Gemini 무료 티어 한도** — 봉마다 호출하면 금방 소진. 대책: ①백테스트는 짧은 구간(예: 60봉) ②호출 실패 시 규칙 폴백(이미 구현) ③결과 캐시 ④비교 실험은 하루 몇 회로 제한
- 결제는 백테스트에서 드라이런(온체인 미전송), 최종 확인만 localnet 라이브

## 3. 로그인 · 회원가입 (신규 요구)

### 3.1 선행 조건 — 배포·영속화가 먼저

지금 엔진은 **프로세스 전역 싱글턴 1개 + 인메모리**다. 로그인만 붙이면 "여러 사용자가 같은 엔진을 공유"하는 구조가 되어 버린다. 순서:

```
① Cloud Run 배포 + Firestore(포지션·거래·브리핑 영속) + Secret Manager(지갑키)
② 인증 붙이기 (로그인 게이트)
③ 사용자별 세션 분리 (엔진 인스턴스·포지션·mandate를 uid 키로)
④ 사용자별 에이전트 지갑 (생성 → 암호화 저장)
```
해커톤 범위 현실안: **①②③까지, ④는 "데모용 서버 커스터디"로 명시**. (사용자별 지갑 자동 생성은 "에이전트는 계좌를 못 열지만 지갑은 코드로 만든다"는 우리 서사와 정확히 맞아떨어지므로, 여유가 되면 강력한 어필 포인트가 된다.)

### 3.2 인증 방식 선택지

| 방식 | 장점 | 단점 |
|---|---|---|
| **Firebase Authentication (권장)** — 구글 로그인 + 이메일/비번 | 비밀번호 저장 책임 없음, GCP 스택과 정합, 구글 로그인 시연이 빠름 | 프론트 SDK 필요 → **외부 CDN 금지 원칙과 충돌** → SDK 파일을 저장소에 vendoring 해서 오프라인 유지 |
| 자체 구현 (FastAPI + bcrypt + 세션 쿠키 + Firestore users) | 외부 의존 0, 완전한 통제 | 비밀번호·세션 보안 전부 우리 책임, 심사 가산점은 없음 |

→ **권장: Firebase Auth + 서버에서 ID 토큰 검증(FastAPI 미들웨어)**. 데모 계정 1개는 심사자용으로 미리 만들어 README에 적어 둔다.

### 3.3 화면·상태
- 비로그인: 랜딩(홈)만 접근 → 로그인/회원가입
- 로그인 후: 대시보드(현 화면), 우상단에 계정 메뉴(로그아웃)
- 세션 소유권: 다른 사용자의 세션 제어·조회 차단(API 전부 uid 검사) — **보안 체크 항목**

## 7. 열려 있는 결정 (사용자에게 물어볼 것)

1. 실데이터 종목·기간·간격, 데이터 파일 커밋 여부 (§1.2)
2. 매매 규칙을 절대가(178/185) → **비율/지표 기준**으로 바꿀지 (§1.3-1)
