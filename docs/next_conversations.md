## 1. Cloud Run 첫 배포 (지금 바로)

**왜 먼저인가**: 첫 배포는 실패 지점이 많고(gcloud 설치·결제 연결·API 활성화·Secret Manager·
Firestore) 시간이 걸린다. 마감 주에 처음 시도했다가 막히면 라이브 URL 가산점을 통째로 잃는다.
한 번 성공시켜 파이프라인을 증명해 두면, 이후엔 로컬 개발 → 마일스톤마다 재배포로 끝난다.

**알아둘 것(이미 확인됨)**: Cloud Run 은 접속해서 파일을 고치는 서버가 아니다. 수정 흐름은
`로컬 수정 → 테스트 → git push → gcloud run deploy(5~10분)` 로 지금과 동일하며, **코드 수정
난이도는 오르지 않는다**(상세 `docs/deploy_cloud_run.md` §7-1).

### 시작 프롬프트

```
저장소: solana-agent (제품명 402 Guard). Cloud Run 첫 배포 전용 대화입니다. 존댓말로.

먼저 docs/next_conversations.md 의 "1. Cloud Run 첫 배포" 절을 읽어 주세요
(왜 먼저인지·완료 기준·배포 시 주의가 거기에 있습니다).

목표: docs/deploy_cloud_run.md 런북을 처음부터 끝까지 따라 배포를 성공시키고,
배포 URL에서 §5 검증(대시보드·persistence.enabled=true·드라이런 세션·Firestore 문서·
재시작 영속 증명)과 §5-1 검증(curl 로 HTTP 402 확인)까지 통과시킵니다.

역할 분담: gcloud 인증·결제·과금이 걸린 명령은 제가 직접 실행하니, Claude는 명령을 한 번에
하나씩 제시하고 제 출력(성공/오류)을 받아 다음 단계를 안내해 주세요. 오류가 나면 런북 §8
트러블슈팅을 먼저 확인하고, 없으면 원인을 짚어 주세요.

그 다음 docs/deploy_cloud_run.md 를 읽고, 제가 지금 어느 단계부터 시작하면 되는지
(gcloud 설치 여부 확인 명령 포함) 알려주세요.
```

**완료 기준**: Service URL 확보 · `/api/state` 의 `persistence.enabled=true` · 재시작 후에도
`/api/history/sessions` 에 세션이 남음 · `curl -i <URL>/broker/orders` 가 402 반환 ·
증빙 스크린샷 확보.

**⚠ 배포 시 주의**: `ALLOW_LIVE_FROM_WEB=0` 으로 두고(시연 직전에만 개방),
`CONTROL_TOKEN` 을 반드시 설정한다(공개 URL 보호).

> **프론트 파일은 기다리지 않는다(2026-07-26 사용자 결정).** 지금 배포되는 건 현재 대시보드이고,
> 프론트를 받아 병합한 뒤 재배포하면 같은 URL 이 갱신된다. 첫 배포를 일찍 성공시켜 파이프라인을
> 증명해 두는 것이 목적이다.

## 1-B. GCP 활용 확대 (배포 성공 직후)

**⚠ 전제 정리(정직하게)**: 확보된 심사 기준(킥오프 전사 + 사용자 제공 공식 기준)에는
**"Cloud Run 을 얼마나 많이 활용했는가"라는 항목이 없다.** 확인된 것은 ①라이브 배포 URL 이
가산점 ②축②가 "Google Cloud AI 스택"을 언급한다는 두 가지뿐이고, 반대로 CLAUDE.md 제약 7 은
"오버 엔지니어링 금지 — 구조적 활용은 가산점이 아니다"로 못박고 있다. 따라서 **서비스 개수를
늘리는 것이 목표가 아니라, 실제 결함을 해결하면서 활용 폭도 넓어지는 것만 고른다.**

### 채택 (가치 순)

| # | 항목 | 왜 — 이건 실제 문제를 해결한다 | 크기 |
|---|---|---|---|
| **A** | **Cloud Storage 로 아티팩트 영속화** | Cloud Run 파일시스템은 tmpfs 라 배포본에서 만든 `artifacts/tx/*.json`·브리핑이 **재시작하면 사라진다**. 즉 지금은 "배포 URL 에서 실행한 증빙"을 남길 수 없다(축④ 실제 구동 증빙의 구멍). GCS 버킷 업로드로 닫는다 | 중 |
| **B** | **Cloud Logging 구조화 로그** | 지금은 `print` 라 콘솔에서 severity·필드 필터가 안 된다. JSON 구조화 로그로 바꾸면 GCP 콘솔에서 "결제·차단·판단" 로그를 걸러 보여줄 수 있다 — **"실행 로그 기반 실제 구동"(축④) 을 콘솔 스크린샷으로 증빙** | 소 |
| **C** | **Cloud Monitoring 업타임 체크 + 알림** | 심사 기간 내내 라이브 URL 이 살아있는지 감시. 죽으면 메일. 무료 티어. 데모 당일 안전장치 | 소 |
| **D** | **Vertex AI 경유 Gemini 검토** | `agents/gemini_decider.py` 가 이미 `vertexai=True` 모드를 지원한다. Vertex 경유가 **$300 크레딧으로 결제되는지 확인**되면, 무료 티어 한도 문제(481봉 백테스트에서 폴백 29건)가 사라지고 축②의 "Google Cloud AI 스택" 요건도 문자 그대로 충족된다. **단 확인 전에는 단정 금지** — 안 되면 무료 티어 그대로 간다 | 조사 후 판단 |

### 배제 (장식적 — 마감 8일 전에 붙이면 리스크만)

Cloud CDN · Load Balancer · 커스텀 도메인 · Pub/Sub · BigQuery · Cloud Tasks · VPC.
우리 규모(단일 인스턴스·소수 사용자)에서 아무 문제도 해결하지 않는다.

### 시작 프롬프트

```
저장소: solana-agent (제품명 402 Guard). GCP 활용 확대 대화입니다. 존댓말로.
Cloud Run 배포는 이미 성공한 상태입니다.

목적: 서비스 개수를 늘리는 게 아니라, 배포본의 실제 결함을 해결하면서 GCP 활용 폭도
넓히는 것입니다. docs/next_conversations.md 의 "1-B. GCP 활용 확대" 절을 먼저 읽어 주세요.

우선순위:
A. Cloud Storage 아티팩트 영속화 — Cloud Run 이 tmpfs 라 배포본에서 만든 artifacts/tx JSON·
   브리핑이 재시작하면 사라집니다. 축④ 증빙의 구멍이라 이걸 먼저 닫습니다.
B. Cloud Logging 구조화 로그 — print 를 JSON 구조화 로그로. 콘솔에서 결제·차단·판단을
   필터링해 보여줄 수 있게.
C. Cloud Monitoring 업타임 체크 — 라이브 URL 감시 + 알림.
D. Vertex AI 경유 Gemini 가 $300 크레딧으로 결제되는지 조사(gemini_decider 는 이미
   vertexai=True 모드 지원). 되면 무료 티어 한도 문제가 해결됩니다. 확인 전 단정 금지.

A 부터 하나씩 구현→검증→커밋→푸시로 진행하고, 각 항목마다 gcloud 명령이 필요하면
제가 실행할 수 있게 한 번에 하나씩 제시해 주세요. 로컬 실행(GCS 미설정)에서는 기존처럼
파일로 저장되도록 폴백을 유지해야 합니다.
```

**완료 기준**: 배포본에서 세션을 돌린 뒤 재시작해도 GCS 에 증빙이 남음 · GCP 콘솔 로그에서
결제·차단 이벤트 필터 조회 가능 · 업타임 체크 동작 · Vertex 결제 가능 여부 결론 기록.

**⚠ 원칙**: 모든 항목은 **로컬에서 GCP 없이도 그대로 동작**해야 한다(Firestore 가 이미
`FIRESTORE_ENABLED=0` 기본 no-op 인 것과 같은 패턴). 로컬 개발이 GCP 에 묶이면 안 된다.

## 3. 차트 강화 — MA200·슬라이드·표시 범위 (2번 완료 후)

> **미룰 수는 있어도 버릴 수 없는 항목이다(사용자 확인, 2026-07-26).** 지금은 재생 데이터라
> 90봉으로 버텨도 되지만, **나중에 실제 주식 시세를 끌어오면 MA100·MA200 같은 장기 추세선이
> 판단과 표시의 기본**이 된다. 프론트 파일 수령이 늦어져 이번 마감에서 밀리더라도, 백엔드
> 버퍼 확장(아래)만이라도 먼저 해두면 나중 작업이 반으로 준다.

**조사 결과(2026-07-26)**: 프론트가 `[1, 5, 10, 20, 50]`만 그리는 게 표면 원인이지만,
**백엔드 `web/engine.py:52 MAX_CANDLES = 90`** 때문에 캔들이 90개뿐이라 MA200 은 수학적으로
그릴 수가 없다. 과거를 못 보는 것도 같은 원인이다. **백엔드 버퍼 확장 + 프론트 인터랙션이 한 세트.**

- 백엔드: `MAX_CANDLES`·`MAX_PRICE_POINTS` 확장(MA200 + 표시 범위 여유 = 최소 300~400봉),
  워밍업 봉을 더 실어 보내기, 메모리·SSE 페이로드 크기 확인. `market/indicators.py` 는 이미
  MA1~200 지원(`ma_snapshot`).
- 프론트: MA 선 200까지 확장(선이 5개→7개 이상이면 범례·색 정리 필요), 가로 스크롤/드래그로
  과거 조회, 표시 봉 수 선택(예: 60/120/250/전체).

### 시작 프롬프트

```
저장소: solana-agent (제품명 402 Guard). 차트 강화 전용 대화입니다. 존댓말로. 프론트/백엔드 둘 다 편집합니다.

## 5. 거래량 + 멀티 타임프레임 (분/일/주/월봉) — **큰 작업**

**조사 결과(2026-07-26)**: `Bar.volume` 필드가 **이미 존재하고 CSV 에서 읽고 있는데 아무 데서도
쓰이지 않는다** — 지표(`market/indicators.py`)에도, 차트 전송 payload 에도, Gemini 프롬프트에도
없다. 주봉·월봉 리샘플링도 없다.

**⚠ 착수 전 반드시 합의할 것 2가지**

1. **1/5 골든크로스 성능 저하의 원인 진단은 절반만 맞다.** 주 원인은 5일선이 너무 짧아 생기는
   **휩쏘(속임수 신호)** 이고, 거래량은 그 신호를 걸러내는 *필터*로 쓸 때만 도움이 된다
   ("거래량 동반 돌파만 인정" 같은 규칙). 거래량을 넣는다고 자동으로 좋아지지 않는다 —
   **필터 규칙을 정하고 백테스트로 검증해야** 개선 여부를 말할 수 있다.
2. **합성 인트라바에는 진짜 거래량이 없다.** `IntradayReplayFeed` 는 가격만 합성하고 거래량은
   일봉 값 하나뿐이다. 여기에 거래량 지표를 얹으면 없는 데이터를 지어내는 것이므로
   **인트라바 경로에는 적용하지 않는다**(적용한다면 "합성 거래량"임을 화면·문서에 명시).
   실 인트라데이 데이터는 무료 티어로 2022 하락장 구간을 못 덮는다(기존 실측, `docs/intraday_synthesis.md`).

**작업 범위 제안(하위 단계로 쪼개 커밋)**: ①거래량 파이프라인(지표·차트 payload·프롬프트) →
②주봉·월봉 리샘플링(일봉에서 결정론적으로 생성) → ③거래량 필터 규칙 1~2개 설계 →
④백테스트로 개선 여부 실측(개선 없으면 **정직하게 옵션으로만 남긴다**).

### 시작 프롬프트

```
저장소: solana-agent (제품명 402 Guard). 시장 데이터 심화(거래량·멀티 타임프레임) 대화입니다.
존댓말로. 백엔드 중심입니다.

사용자 문제 제기: 분봉/일봉/주봉/월봉, 매매량 같은 것이 시세·매매 판단의 근거로 매우 중요한데
